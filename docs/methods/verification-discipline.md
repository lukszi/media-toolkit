# The verification discipline

**Implemented by `mkvkit.verify` (`mkvkit verify`), `mkvkit.propedit`
(`mkvkit propedit`), `mkvkit.probe` (`mkvkit probe`) and `mkvkit.swap`
(`mkvkit swap`).** Every rule below is a function or an assertion in one of
those, not a paragraph somebody is expected to remember. Where a rule is not
implemented, it says so.

This is the most transferable thing in this repository and it is not about
Matroska. It is about what it takes to believe that a program did what it said
to a file you cannot get back.

---

## 1. "The command exited zero" is not verification

An exit code says a program reached its end without raising. It does not say
the file it produced is the file you wanted, and for at least three tools here
it does not even say the file changed:

- the header editor exits zero on a container it cannot write, having done
  nothing;
- the muxer exits one -- "warnings" -- for conditions that range from
  cosmetic to "your output has no index";
- a probe exits zero on a file whose tail is all zeroes, because its header
  is intact.

Neither is a size comparison. A rebuilt file legitimately has a different
size; a check that cannot fail is worse than no check, because it is recorded
as a pass.

**What counts as evidence**: a measurement of the thing you care about, taken
on both sides, compared against a difference you declared **before** you
looked.

## 2. Declare the difference first

The useful question is never "are these two files the same?". It is "is the
difference between them exactly the one I intended?".

So the intended difference is an argument to the comparison:
`TracksDropped(dropped={3})`, `TracksAppended(count=1)`, `HeaderOnly()`. Then
every difference outside the declaration is a failure by construction, rather
than something somebody has to notice.

This is also the only thing that makes a verification re-runnable by a person
who was not there: the declaration is the intent, written down.

```python
rebuild = plan(found, policy, output=staged, original_language="eng")
result = compare(collect(source), collect(staged), rebuild.expected_delta())
```

The plan hands the comparison its own declaration, so the two cannot drift.

## 3. Prove identity at the payload level, on both sides

Ask the decoder for one hash per stream, with a stream copy -- no decoding, no
re-encoding -- on both files. Drop the deliberately removed streams from the
original's list. Compare the ordered lists, and locate a mismatch by position:
*this hash was that stream*.

Check the exit code on both sides too: a non-zero exit with a plausible list of
hashes is a failure, not a pass.

This is a full read of both files and it is the expensive step of any
verification. Two practical notes: read the two sides from **different
physical disks** and the reads cost nothing extra; and when a *video* hash
differs, that is not yet a re-encode -- compare the per-frame hashes, because a
container that re-states its parameter sets changes those bytes and not one
picture.

## 4. Know what cannot have changed, and skip measuring it

A header editor cannot touch a packet payload. After a header edit, then, the
payload hashes from before the edit are still true, and re-reading two
multi-gigabyte files to confirm it measures something that provably did not
change.

`reheader()` refreshes the header half of the evidence and keeps the hashes
somebody already paid for. This is not a shortcut. A verification that takes
an hour gets skipped; one that takes a second gets run, and the discipline is
whatever actually gets run.

The rule generalises: for every expensive measurement, ask what the operation
was *capable* of changing.

## 5. Record the cosmetic differences, with their reasons

A comparison that fails on differences that cannot matter trains everybody to
ignore it. A comparison that ignores them silently hides the one that did
matter. So they are **notes**, each carrying the reason it is a note:

- a modern language subtag appears while the legacy element is unchanged --
  the legacy element is what most readers use, so it is compared strictly, and
  two files carrying *different* modern subtags still fails;
- identifiers regenerated by the muxer -- nothing outside the file references
  them, and tags targeted at them are remapped;
- a container that got **shorter** while every kept payload hash matched --
  the dropped track ran past the rest, which is what removing it looks like. A
  duration that *grew* is still a failure.

Writing the reason next to the exemption is what stops the exemption list from
widening. Every one of these was earned by a file that failed for no reason.

## 6. Compare the thing, not its serialisation

Chapters are compared as count, start time to a millisecond, and name -- never
as the raw document, which differs on every rewrite for reasons that mean
nothing. Tags are compared as `(track identifiers, name, value)` triples, for
the same reason, and across a rebuild the identifiers have to be translated
first because the muxer regenerates them.

The general form: find the normal form of what you actually care about, and
compare that. Anything finer reports noise, and a real difference hides in
noise.

## 7. Every writing operation produces its rollback before it writes

Not after, and not "if something goes wrong": before, always, whether or not
the write is even going to happen. It is one read, and it cannot be
reconstructed afterwards.

For a header edit that is the inverse of every property being changed, plus
the chapter and tag documents the file had. For a chapter naming pass it is
the same marks with the names stripped. For a file swap it is the original
file itself, moved to a parking directory and kept.

Generating the rollback is a line of code. Applying it is a decision somebody
makes later, with the evidence in front of them.

## 8. Dry run is the default, and there is no third state

Every function here that writes takes `dry_run=True` by default and every
command takes `--dry-run` (the default) and `--apply`. No environment variable
flips it, and no configuration key weakens it. The one `--force` there is
lets `chapters match --out` or `chapters rollback --out` replace a document it
wrote earlier; nothing lets a write skip the dry run.

The dry run is not a cut-down path: it produces the same plan, the same
command, the same rollback and the same refusals as the real run, and then
stops. That is what makes it worth reading.

## 9. Run a known-answer control before trusting a measurement

A measurement pipeline that has never been tested against an answer you
already know is a pipeline that produces numbers, not measurements. The
controls are cheap: a track against itself must read zero; a synthetic pair
with a known offset must recover that offset; the same pair measured at two
points in the timeline must give the same answer.

The same applies to a gate: a privacy scan that has never failed is not known
to work, which is why this repository's own scan has a test that plants
secrets in a file and requires them to be caught.

## 10. Prefer a no-op to a confident wrong answer

Where the evidence does not settle, the answer is "unsettled" and the file is
left alone. A tool that writes its best guess into somebody's collection is
worse than one that writes nothing, because the guess is indistinguishable
from a decision afterwards.

This is why an unnamed chapter is written with no name rather than with the
label a player would have shown; why a language that does not settle is
queued rather than written; and why the verification's verdicts include
"uncertain" and treat it as a stop.

## What is not implemented

- **A full sequential decode as a corruption oracle.** The findings behind
  §1 came from one; there is no command here that runs it yet.
- **The parallel two-disk read.** The throughput observation is real and the
  scheduling that exploits it is in `jfkit.jobs`, not here.
- **A verification report format.** `Comparison` prints; it does not yet
  serialise to the survey schema the rest of the toolkit uses.
